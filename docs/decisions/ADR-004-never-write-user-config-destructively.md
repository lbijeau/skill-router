# ADR-004: Never write user config destructively

## Status
Accepted

## Date
2026-11-13

## Context
`install`/`update` edit files the user owns and may have hand-edited:
`~/.pi/agent/settings.json`, `~/.vibe/config.toml` (or `$VIBE_HOME`), and
`~/.claude/settings.json`. These files hold unrelated settings the installer
does not understand; corrupting them breaks the user's tools beyond this
project. TOML in particular can carry comments, multi-line arrays and
multi-line strings that a naive parse-and-rewrite would silently destroy.

## Decision
Every user-config write is additive, atomic, and refuses what it cannot
merge safely:

- **Atomic writes**: all config writes go through `atomicWrite`
  (temp file, then rename) in `scripts/common.mjs`, so a crash never leaves
  a half-written settings file.
- **Backups**: a `.bak` copy is written before each merge (pi settings,
  Vibe config, Claude settings — the Claude copy at mode 0600). An
  unparseable settings file is never touched.
- **Safe-bail on unrecognized formatting**: `mergeVibeConfig` refuses
  multi-line arrays (a trailing comma or an array opener at end of line),
  multi-line strings (`"""` / `'''`), duplicate `agent_paths` /
  `allowlist` keys, and any `[tools.read_file]` spelling outside the
  recognized header forms (array-of-tables, dotted keys, inline tables).
  Each refusal prints the exact manual remedy — the line to add and where —
  instead of guessing.
- **Ownership for Claude files**: the installer only overwrites files it
  owns (marker line `<!-- generated by skill-router -->`, `name` matching
  the filename, not a symlink); everything else is reported and left alone.

## Alternatives Considered

### Parse and rewrite the whole file with a real TOML/JSON library
- Pros: handles every valid file; no bail-outs.
- Cons: a canonicalizing rewrite reorders keys, reformats arrays, and can
  drop comments — a destructive change to a file the user owns, even when
  the parse succeeds.
- Rejected: preserving the user's formatting matters more than full
  coverage; the line-wise merge plus printed remedy covers the rest.

### Append-only edits
- Pros: never touches existing lines.
- Cons: duplicates on re-run; appending inside a multi-line array produces
  invalid TOML.
- Rejected: appending is only safe for a file shape the merger cannot
  verify.

### Trust the file to match the expected shape
- Pros: simplest code.
- Cons: one unusual config (multi-line array, inline table) and the merge
  corrupts the file or fails at runtime.
- Rejected: user config corruption is the worst failure mode an installer
  can have; the conservative envelope is the design.

## Consequences
- A user whose config uses an unmergeable form applies one printed line by
  hand, once; the installer stays out of the way after that.
- The merge envelope is deliberately small; growing it means adding a
  recognized form plus a test, never loosening a guard.
- `settings.json.bak` is overwritten by each merge (a one-deep backup, not
  a history) — accepted and documented as a deferred-by-design leftover.
- The temporary file `atomicWrite` stages exists for a few milliseconds at
  the default mode before being set to 0600 and renamed (also documented as
  a known leftover).
